# Linux io_uring transport evaluation — 2026-09-17

T405 result: retain readiness-based production I/O. Five alternating pairs per
case did not show a consistent CPU or write-tail improvement at 60 FPS.
Unpaced batching improved some cases, but this does not justify replacing
Tokio or the C FIFO writer. No production io_uring dependency was added.

## Measured results

The following are medians of five trials. CPU is total process CPU, including
producer, receiver threads and byte verification, across approximately 1.98
seconds / 120 frame batches. Write p99 is the nearest-rank percentile of each
trial's time to finish the writes to **all** channels in a frame batch; the
table takes the median of those five p99 values. It measures kernel acceptance
of ordinary writes, not Android receipt, rendering or acknowledgment.

| Transport | Sessions | CPU ms: poll → io_uring | Write p99 ms: poll → io_uring |
| --- | ---: | ---: | ---: |
| pipe | 1 | 76.31 → 81.40 | 0.525 → 0.715 |
| pipe | 2 | 155.88 → 146.88 | 0.854 → 0.768 |
| pipe | 4 | 291.38 → 287.88 | 2.098 → 1.837 |
| tcp | 1 | 7.88 → 8.09 | 0.058 → 0.061 |
| tcp | 2 | 12.79 → 13.76 | 0.069 → 0.067 |
| tcp | 4 | 23.49 → 23.03 | 0.100 → 0.089 |

These pipes use the production helper's best-effort 1 MiB capacity request;
the effective capacity was 1,048,576 bytes for every pipe trial. CPU results
remain mixed: two paced pipes improved by about 5.8%, while one paced pipe
regressed by about 6.7%. Four paced TCP streams improved about 2%, with one and
two streams regressing. These small/uneven differences do not establish a
production advantage. No battery or complete UScreen gain is established.

The earlier replay with default 64 KiB pipes is preserved as a separate series
with its exact harness source. It also had mixed outcomes, including an
unpaced four-TCP CPU improvement, and is superseded for the raw-pipe comparison.
TCP absolute timings differed substantially between the two series despite
unchanged TCP setup. Do not attribute that difference to pipe sizing or code
changes: the series ran at different times on a shared host. Use within-series
paired comparisons and repeat realistic workloads before adopting a backend.
All 120 trials from each series are retained.

## Method and limits

[`io-uring.c`](../../scripts/benchmarks/io-uring.c) compares optimistic
nonblocking writes plus `poll` with ordinary io_uring WRITE/SEND operations.
It uses one outstanding write per channel, handles partial writes and EAGAIN,
and queues independent channels together. Receivers verify sequence headers
and every payload byte. The experiment uses anonymous pipes for the raw FIFO
I/O mechanism (not FIFO reopen/lifecycle behavior) and actual loopback TCP,
with 1/2/4 channels, paced/unpaced work and five paired trials for 12 cases.
Pipe capacity is recorded; a failed enlargement keeps the available capacity.

Raw payloads are 1,536,000 bytes including an eight-byte synthetic sequence
header; TCP payloads are 65,536 bytes including that header. These are fixed
synthetic sizes, not captured access units or the exact UScreen wire protocol.
Source buffers stay immutable while writes are outstanding. No SQPOLL,
registered buffers, multishot I/O or zero-copy send is used. Initialization and
payload allocation precede timing; receive draining and verification are timed.

Host: AMD Ryzen 9 7945HX, 32 allowed logical CPUs, Linux 7.0.0-31-generic,
GCC 13.3.0, liburing 2.5-1build1 extracted to temporary storage, no system
package installation. Runs were serial, without other agent benchmarks or
compilation, on the existing desktop. OS activity, CPU frequency, pipe/socket
capacity, thread placement and receiver work can affect results. The baseline
is a small readiness loop, **not** a reproduction of Tokio's reactor. Per-frame
batch barriers also differ from independent production sessions. Results are
specific to this harness, kernel and host.

## Applicability and ownership

The host successfully created a default ring and advertised READ, WRITE, SEND,
RECV, ASYNC_CANCEL and SEND_ZC. Applications still need runtime probes and a
fallback when a kernel, container policy or operation rejects io_uring.
Distro independence must not become a dependency on one distribution's kernel
configuration. Android and the planned Windows host need separate adapters.

io_uring changes submission/completion handling; ordinary I/O does not by itself
remove raw FIFO or socket payload copies, accelerate BGRA conversion, or bypass
ADB. Independent streams can batch work, while each stream must preserve
framing order. Outstanding request buffers must remain owned until completion,
including during cancellation. SQPOLL adds a polling kernel thread; its CPU
cost must be included in a separate experiment. See the
[Linux io_uring API](https://man7.org/linux/man-pages/man7/io_uring.7.html) and
[cancellation API](https://man7.org/linux/man-pages/man3/io_uring_prep_cancel.3.html).

Zero-copy sends have an additional notification/lifetime contract, and a
successful send is not proof that copying was avoided. Linux documents deferred
copies for MSG_ZEROCOPY packets sent to local TCP sockets. The current host
connection ends at local ADB, so ordinary ring batching and zero-copy send must
be evaluated separately; see [zero-copy sends](https://man7.org/linux/man-pages/man3/io_uring_prep_send_zc.3.html)
and [kernel loopback limitations](https://docs.kernel.org/networking/msg_zerocopy.html).

Before any future production adoption, require cancellation races, partial
frames, EOF/HUP, FIFO replacement, mode changes, socket retirement and delayed
completion tests, plus realistic CPU, retained-memory and end-to-end traces.
This measurement does not certify those integration contracts. T405's actionable
readiness/cancellation work remains open.

## Reproduce

Install/expose development headers for liburing only for this optional replay:

```sh
python3 scripts/benchmarks/io-uring.py --trials 5 --output /tmp/uring.json
```

Alternatively pass `--include /path/to/include --library /path/to/liburing.a`.
The [compressed raw results](2026-09-17-io-uring/results.json.gz) contain build
arguments, host affinity, source SHA-256 and every trial. The directory also
contains the opcode availability record and SHA256SUMS. Reruns need not match
these timings; investigate comparable workload results rather than treating
these medians as universal thresholds.
