# Raw input ownership and transport — 2026-09-18

T389 removes an input staging copy from the optional in-process encoder for
contiguous NV12 planes, adds release notification for native frame retirement,
and evaluates shared memory and page allocation independently. The default
stock-FFmpeg CLI remains supported and unmodified. No desktop display was
attached or restarted for these experiments.

## Production changes

`encoder_frame.rs` owns writable input preparation independently of codec
submission. Before acquiring mutable plane slices, it calls stock
`av_frame_make_writable`; retained encoder references therefore keep their old
pixels. When both strides equal the visible width, the FIFO reader fills Y and
UV planes directly. It carries one logical packed offset across the two planes:
EOF discards the entire partial frame, and cancellation never submits it.
The IDR request is consumed after a complete input read, preserving requests
that arrive while waiting for capture. Submission, PTS and packet publication
remain in the encoder.

Stride-padded widths retain one reusable packed staging buffer and row copies.
Reading a short row per syscall can cost more than the removed memcpy. The
contiguous copy helper uses one slice copy per complete plane and preserves
the existing behavior for incomplete final rows. Direct filling removes one
userspace frame copy and its staging allocation; it still copies data across
the kernel FIFO boundary. libavcodec can also allocate/copy when detaching a
retained frame. This is not end-to-end zero-copy.

Native `frame_exchange_retire` now waits on the existing condition variable
with one absolute monotonic one-second deadline. Release owns the mutex and
broadcasts the changed predicate. Spurious notifications cannot extend the
deadline; timeout still retains every leased allocation. Writer admission,
generation invalidation and T226 interrupted-write recovery are preserved.

The old encoder comments claimed that FFmpeg's small reads explained historical
337% CPU and that requesting a whole frame meant four syscalls. Neither claim
was established. Read counts depend on actual pipe capacity and producer
progress. The new comments state the boundaries without attributing unmeasured
CPU use. The capture allocation comment likewise distinguishes accepted
`MADV_HUGEPAGE` advice from observed backing.

## Results

In the final five-round series, direct filling increased saturated 4K raw-input
throughput from 189.9 to 278.6 frames/s with one stream, 259.5 to 438.2 aggregate
frames/s with two, and 285.6 to 448.7 with four. The corresponding median trial
p99 ages fell from 9.795 to 6.306 ms, 14.950 to 8.040 ms, and 25.784 to 14.651 ms.
These are raw-input results, not encoded or displayed frame rates.

The `direct` mode at width 1282 actually exercises the padded staging fallback.
That unchanged copy strategy varied between series: its four-stream final

opposite ordering. This prompted a longer dedicated control, retained with the
artifacts. Ten longer 1000-frame, four-stream trials gave median 7436.9 versus

The isolated 12,441,600-byte ring moved 1966.2 frames/s versus 226.2 for the
ordinary aligned pipe with one stream, and 2500.9 versus 417.0 aggregate frames/s
with four. Median trial p99 ages were 0.968 versus 7.258 ms and 3.103 versus
14.528 ms respectively. It removes the two kernel pipe copies in this synthetic
producer/consumer experiment. The much larger gains for the 1,536,000-byte case
are especially cache-sensitive and cannot be applied to a full encoder workload.
The production integration remains T418; the measured prototype is not enabled.

Anonymous huge-page advice produced 6144/36864 KiB of observed huge backing in
the small/large three-slot allocations. First-touch minor faults fell from
roughly 1544/9224 to 11/26. The warm pipe throughput remained close to ordinary
pages rather than showing a comparable step change. Both memfd variants showed
zero huge-page backing under the current shmem policy despite accepted advice.
No new huge-page requirement, sysctl change or explicit hugetlb allocation is
justified by this experiment.

A separate paired retirement replay holds a writer lease for 10, 100 or 900 ms.
Median old polling counts were 11, 97 and 856; each candidate used one condition
wait and no polling sleeps. Median completion after release changed from
486/993/342 µs to 7/18/25 µs. With the lease held 1100 ms, the old 1000-sleep
loop returned after about 1053 ms, while the candidate's absolute timeout
returned after about 1000 ms. These are scheduler-dependent observations;
the permanent test validates the deadline and storage-retention contract.

## Measurement scope

The Rust replay builds the actual candidate input adapter, readiness reader and
FFmpeg frame wrapper. It extracts the old row-copy implementation from
`8c3279b`, and compares `rows`, `contiguous`, and `direct` in one executable.
It uses stock FFmpeg 5.1.9 through ffmpeg-next 9, Rust 1.90, and the Debian 12
`uscreen-ci:perf` image. Every stream has a real nonblocking FIFO, one producer
and one consumer. Requested/effective pipe capacity is recorded. All modes
share the current readiness implementation, so this isolates input storage
rather than repeating T405's polling comparison.

Cases are 1280×800, 1920×1080, 3840×2160 and stride-padded 1282×800, each at
1/2/4 concurrent streams. Each trial has 32 warmup and 180 measured frames;
five rounds alternate variant order. Input is a changing uniform byte value,
checked at both ends of every visible plane row. There is no encoding,
compositor capture, USB/ADB transport, Android decoding or physical display in
this timing. It measures saturated throughput, not paced 60 FPS behavior.

The three-frame metadata channel and 1 MiB FIFO bound producer lead. Recorded
age starts immediately before generating each raw frame and ends after input
preparation; it includes producer fill and any backlog. CPU sums producer and
consumer thread clocks, including read calls and verification. Consumer-only
fault/context-switch counts are labeled separately. Thread-start setup is
outside timing. Producer and consumer phase boundaries are slightly offset by
the bounded pipeline; do not interpret their CPU totals as isolated memcpy time.

The C transport prototype separately compares a real pipe with a three-slot
`memfd` ring. The producer creates its memfd after `fork` and passes it with
`SCM_RIGHTS`; the consumer does not inherit that descriptor. Size seals prevent
shrinking/growing, the consumer maps pixel storage read-only, and acquire/release
atomics plus sequence-checked acknowledgements prevent overwrite before release.
A private sequenced socket carries bounded notifications; the prototype does
not spin waiting for a free slot. It uses ordinary Linux APIs, no codec patch.

Both transports generate all frame bytes with `memset`; the consumer checks one
byte per 4096-byte span plus the last byte. This deliberately isolates transport:
an encoder would read substantially more memory, and capture/conversion do more
work than memset. Small rings can fit in CPU caches. These results are evidence
for a production experiment, not display FPS or a complete shared-memory backend.
T418 retains that integration and its missing lifecycle/encoder evidence.

The allocation comparison prefaults equally sized, rounded three-slot regions:
2 MiB-aligned ordinary allocation, anonymous mmap with ordinary-page advice,
and anonymous mmap with huge-page advice. The ring compares ordinary memfd and
huge-page advice on memfd. It records first-touch duration/faults and actual
`AnonHugePages`/`ShmemPmdMapped` counters, rather than assuming advice succeeded.
The host policy is anonymous THP `madvise`, shmem `never`; no global setting or
hugetlb reservation is changed. Normal pages remain usable on every path.

All runs use the Ryzen 9 7945HX workstation with 32 allowed logical CPUs and
Linux 7.0.0-31-generic. The desktop and separate Android decoder experiment
remain active; affinity/frequency are not pinned. Repeat ranges and raw records
are retained so small variations are not presented as certain gains.

## Backend design and limits

A production shared ring must carry a versioned descriptor with bounded total
size, pixel format, dimensions, plane offsets/strides, slot count, session nonce,
generation and sequence. Validate arithmetic and all ranges before mapping or
publishing pointers. Protect mapping size with seals. A producer reserves a free
slot, converts directly into it, then publishes ready with release ordering;
the consumer acquires that state and holds a read lease. Reuse occurs only after
the final encoder reference releases it. Acquire/release state changes must be
lock-free across these processes or the backend must fall back safely.

Use a read-only `AVBufferRef` with a lease-release callback to back the NV12
`AVFrame`. Its owner retains the mapping and generation through every encoder
reference, including delayed output. Stop closes admission and wakes blocked
owners; peer EOF retires the session. Resize creates a new sealed mapping and
generation instead of truncating live slots. Late completions from an old
mapping cannot free new-generation slots. An unavailable/full ring applies
bounded backpressure or coalesces whole unencoded frames, never overwrites a
leased slot. Wire metadata must use explicit field sizes/order rather than
assuming C/Rust struct padding. Descriptor admission, state transitions and
crash recovery require the tests in T418 before production enablement.

Linux memfd supplies RAM-backed file descriptors, mapping and seals; descriptor
handoff and lifetime still belong to the application. Size seals prevent a
peer shrink from invalidating mapped storage. They do not make a mutable frame
immutable while the producer retains write access; the lease protocol provides
that guarantee. [Linux memfd documentation](https://man7.org/linux/man-pages/man2/memfd_create.2.html).

A framed FIFO could carry timestamps, generation, format and length for the
in-process reader and improve explicit validation. Rawvideo FFmpeg CLI input
cannot accept those headers unchanged; a framing adapter would still need to
feed a normal raw byte stream. Writes larger than PIPE_BUF are not atomic;
length validation, partial-read handling, inode replacement and cancellation
remain necessary. This improves observability/recovery but does not eliminate
the producer-to-kernel-to-consumer copies. The stock CLI remains the portable
fallback while shared-memory ownership is evaluated separately.

PipeWire advertises virtual monitor capture through the portal's VIRTUAL source
type when the installed backend supports it. The current Cinnamon session's
portal returns “No such interface org.freedesktop.portal.ScreenCast”; that is
an observed local limitation, not a claim about all Cinnamon or Linux systems.
No portal session or new display was created.
[ScreenCast contract](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html).

DMA-BUF needs compatible pixel formats, plane layouts, modifiers, devices and
synchronization. Negotiate the format/modifier intersection and retain a shared
memory fallback. Tiled/compressed buffers cannot be assumed linear after mmap;
CPU mapping a discrete GPU buffer can be slow. Keep the PipeWire buffer leased
until conversion/encoding completes, and honor implicit or explicitly negotiated
fences. [PipeWire DMA-BUF negotiation](https://docs.pipewire.org/devel/page_dma_buf.html),
[Linux buffer synchronization](https://docs.kernel.org/driver-api/dma-buf.html).

A GPU path would import the producer's actual buffer into a matching hardware
context, convert/scale there, and submit hardware frames to a compatible encoder.
Current EVDI userspace capture yields CPU BGRA and the optional encoder submits
software NV12; adding mmap does not create a DMA-BUF or VAAPI context. The
optional VAAPI rejection and uncapped CQP behavior remain; T259 later made
the bitrate limitation explicit in settings. Hardware-frame import,
cross-GPU transfers and fences need independent validation on supported desktops;
there is no measured DMA-BUF gain in this report.

THP can reduce translation/fault overhead, but advice, allocation/compaction cost
and actual backing depend on kernel policy and memory state. The observed
anonymous-page result cannot be transferred to shmem or the EVDI driver's copy
path without measurement. [Kernel THP documentation](https://docs.kernel.org/admin-guide/mm/transhuge.html).


## Validation and reproduction

Seven permanent Rust T389 tests cover actual read destinations inside writable
AVFrame planes, zero aligned staging capacity, retained references, fragmented
input, EOF between planes, cancellation during chroma, padded pixels and padding,
complete-row copy semantics, and identical encoded H.264 bytes from direct and
staged input. The read-destination test failed against the staged adapter before
the optimization and passes unchanged. The normal T266 retained-frame test,
T027/T226 recovery checks and uncapped VAAPI CQP behavior remain.

The permanent native T389 regression failed on the old polling implementation
and passes with notification. It checks spurious wakeups, one unextended deadline,
bounded timeout and retention of leased storage under ASan/UBSan. All 248 default
host tests, 234 optional-encoder tests, 31 helper tests, five conversion tests,
the independent native module test and the retirement test pass. Both all-target
Clippy builds pass with warnings denied. The native helper compiles with
`-Wall -Wextra -Werror`; it was not executed against a display. The final
complexity scan found no function above nine. Ignored tests in the host suites
are existing explicitly invoked benchmark harnesses, not skipped regressions.

The [artifact directory](2026-09-18-raw-input/) retains the final 180 raw-input
trials, 100 ring/allocation trials, 24 retirement trials and 30 longer padded
control trials, plus the initial full series, summaries/ranges, original source
snapshots, manifest/lockfiles, executable hashes and validation logs. Final
raw/ring series ran after the full native build/test gate. The workstation and
Android replay remained active; the later padded control also overlapped a brief
helper/complexity verification. No isolated-machine or optical-latency claim is
made. CPU and initial page-fault measurements are supporting observations, not
the acceptance criterion for a host with ample resources.

Use an environment with the recorded stock FFmpeg development libraries, Rust,
C compiler and cached crate dependencies. New build/output directories avoid
cross-revision artifact reuse:

```sh
python3 scripts/benchmarks/raw-input.py \
  --directory /tmp/new-raw-input --output /tmp/new-raw-input.json
python3 scripts/benchmarks/raw-ring.py \
  --directory /tmp/new-raw-ring --output /tmp/new-raw-ring.json
python3 scripts/benchmarks/summarize-raw-input.py \
  --raw /tmp/new-raw-input.json --ring /tmp/new-raw-ring.json \
  --output /tmp/new-raw-summary
cargo test --locked -p uscreen --features inproc-encoder --bin uscreen t389_
cargo test --locked -p uscreen --test frame_retirement
```

The raw-input builder uses offline Cargo resolution and preserves its generated
lockfile. For the exact recorded dependency set, use the archived manifest and
lockfile. The ring driver records the compiler, kernel THP policies, binary
hash and per-stream raw observations; it makes no system policy changes. The
retirement snapshot contains both exchange revisions and the C harness; compile
with `-DEXCHANGE_SOURCE="/absolute/path/to/frame_exchange.c"` and `-pthread`,
then pass the held-lease duration in milliseconds. The padded-control driver is
also preserved for exact repetition.
