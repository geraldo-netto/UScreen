# Timing bookkeeping — 2026-09-17

T404 fixes timing publication across threads and decoder replacement, then
accelerates bounded lookups and reuses host report buffers. The changes preserve
the existing ACK frequency, sequence representation, history bounds and host
ACK eviction rules. The measured improvements concern bookkeeping only: they
do not establish a change in tablet presentation latency, FPS or battery use.

The Android cache helps delayed callbacks but adds a small cost to immediate
callbacks and collisions. Rust's contiguous-sequence lookup removes a scan of
up to 256 entries; its sparse fallback is slower in this build. These tradeoffs
are retained for the ordinary sequential stream and delayed-callback case.
Correct cross-thread and generation ownership is required independently of
these performance results.

## Android lookup replay

The replay builds the actual `FrameTiming` implementation on host OpenJDK 21
with Kotlin 1.9.20. Android logging is stubbed. Three variants are compared:

- `original`: the unguarded implementation from `0533724`, a historical reference
  with the reproduced races described below.
- `scan`: the corrected implementation with its tag-cache lookup disabled.
- `candidate`: the corrected implementation with the validated cache enabled.

Each fresh JVM warms up with 100,000 iterations, then measures 200,000 iterations
per independent session. An iteration records arrival, records output release
and queries callback latency. The objects escape to shared storage; one worker
owns each session during this cost replay. This does not measure cross-thread
contention within a real Android receiver. Separate deterministic tests exercise
that receiver's concurrent publication and retirement.

Five alternating trials cover each of 1/2/4 sessions and five lookup patterns,
for 225 trials. Sequences wrap across the signed integer boundary. Delayed
lookups query eight or 32 arrivals behind; missing queries are 128 arrivals
behind. Sparse sequences advance by 64, deliberately colliding in the tag cache.
All variants return identical timing checksums for these workloads.

## Rust lookup and report allocation replay

The replay uses actual `latency.rs` from `0533724` and the candidate, built with
Rust 1.90 in separate release target directories in the Debian 12
`uscreen-ci:perf` container. Each worker populates its own 256-entry history and
performs two million locked lookup queries. Queries target the first entry,
last entry, an absent sequence, or the last entry of a sparse history. Lookup
results are checked across variants. This isolates lookup cost; it does not
time complete ACK handling, deque draining, network delivery or shared contention.

Thirty additional trials count allocator calls during 100 report windows per
tracker. Each window encodes and acknowledges 64 frames, then reports; two
warm-up windows precede measurement. Reporting runs serially so global allocator
counts exclude worker setup. The candidate makes **zero allocations/reallocations**
after warm-up in every trial. The original makes 200 allocations and 800
reallocations for one tracker, 400/1,600 for two and 800/3,200 for four. Logging
has no subscriber in this replay; production logging can allocate independently.
Growing beyond warmed capacities or overlapping reports can still allocate.

## Correctness and ownership

The old arrival index was volatile, but release slots and diagnostic accumulators
had no shared guard. A release paused after lookup could write into a reused
arrival slot. Arrival publication also preceded receiver-generation validation,
and codec replacement reused timing history. A render callback could pass its
codec check, pause during timing, then acknowledge after replacement.

The corrected implementation guards publication and lookup, validates an opaque
decoder epoch, and checks current codec ownership at ACK emission. Clock sampling
precedes timing-state locking; identity is revalidated when publishing. Arrival
time is sampled before receiver-lock acquisition and recorded only after the
receiver and codec are validated, before waiting for codec input. History remains
the latest 64 arrivals, including duplicate and sparse sequence values; cache
collisions fall back to the newest matching history entry. Slot reuse clears
release state. A valid zero clock value is distinguishable from an empty slot.
Repeated callbacks still return elapsed time and follow the existing ACK rule,
but each arrival contributes at most once to split averages. Render notification
execution remains the endpoint, not a physical-screen timestamp.

Host lookup remains first-match for discontinuous histories. A matching ACK
retires entries through that position; late older ACKs are ignored. Only entries
aged out by the 256-entry bound count as lost. Contiguous lookup handles unsigned
sequence wrap. Reports exchange owned sample vectors under the tracker lock,
sort/log after releasing it, then recycle cleared storage without overwriting
new or overlapping report samples. The 1,024-sample limit, percentile rounding,
decode-value clamp, five-second report interval and log meanings are preserved.

Nine new Android tests cover slot reuse, epoch retirement, stale packet arrival,
an in-flight callback across codec replacement, duplicate callbacks, zero origin,
cache collisions and sequence wrap. Seven behavioral assertions were observed
failing before their fixes. They remain in the normal Robolectric suite on API
27 and 34. Four new Rust tests cover report reuse, sparse/duplicate/wrapped
eviction, overlapping reports and bounded/loss/percentile semantics; the reuse
assertion was observed failing before implementation. Existing T228, T253 and
T376 regressions remain active. Red/green logs are archived.

Full validation: 191 Android unit tests and lint pass; 248 default host tests
pass with one manual benchmark ignored; 227 optional-encoder tests pass with two
manual benchmarks ignored. Both host feature configurations pass strict Clippy.
The complexity gate checks 2,486 functions, none above nine. No application was
installed or restarted for this replay.

## Reproduction

Use empty build directories; `--reuse` runs already-built artifacts. Run each
series after compilation and other test workloads finish, and keep the series
sequential. Kotlin's compiler dependencies use the pinned, hash-checked bootstrap
from the complexity tooling. Rust requires the manifest dependencies cached for
offline builds. Source snapshots, lockfiles, executable hashes, raw results,
environment and validation logs are in the [artifact directory](2026-09-17-timing/).

```sh
python3 scripts/benchmarks/timing-kotlin.py \
  --directory /tmp/timing-kotlin --output /tmp/timing-kotlin.json
python3 scripts/benchmarks/timing-rust.py \
  --directory /tmp/timing-rust --output /tmp/timing-rust.json
```

Both scripts support `--build-only`, `--reuse`, `--count` and `--trials`. The
archived series used their default counts and five trials. Summaries divide
each trial's maximum worker wall time by its iteration count, then take the
median/minimum/maximum across trials. Allocator results are exact counted calls.
