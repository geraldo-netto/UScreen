# Codec quality, buffering and compatibility — 2026-09-18

T400 evaluates stock H.264/HEVC, VP9 and AV1 on the available host and tablet.
No FFmpeg patches or new production wire codecs are introduced. VAAPI's optional
processing depth is reduced to one only when the selected stock encoder
advertises that control. An explicit `h264_vaapi_baseline` option adds Constrained Baseline/CAVLC H.264
to the existing Linux encoder selector. The user chose to preserve the current
selection. VP9/AV1 remain experiments rather than production wire codecs.

## Platform inventory and measurement boundaries

Host: Ryzen 9 7945HX, 32 logical CPUs; RX 6600 XT / Navi 23, Mesa 26.2.2;
stock Ubuntu FFmpeg 6.1.1. The current GPU exposes H.264/HEVC encode capability,
but AV1/VP9 are decode-only in its VAAPI inventory. A listed FFmpeg wrapper does
not prove that the installed GPU can encode that codec. Host validation also
uses unmodified Debian FFmpeg 5.1.9 in the Rust 1.90 CI container.

Tablet: Ulefone RugKing Pad 2 Pro, Android 16/API 36. The read-only codec inventory
uses `MediaCodecList`, preserving hardware/software flags, aliases, profiles,
levels, dimension/rate queries and maximum advertised instances. H.264/HEVC
have Unisoc hardware decoders (advertised ten instances), VP9 has a hardware
decoder (twenty), and AV1 is software-only. These instance counts are capability
reports, not measured simultaneous decoder limits. No standard low-latency
feature is advertised by the measured Unisoc decoders.

Physical replays use a separate debug APK, app brightness 0.5 and observed 60 Hz,
with the same USB source attached. The main application, host daemon, EVDI and
Cinnamon remain installed/running unchanged. Decoder samples are already encoded
and memory-resident: they exclude capture, encoder latency and USB/Wi-Fi video
transport. Encoder pacing experiments independently exclude Android. Their
percentiles cannot be added to claim capture-to-display latency.

## Comparable quality floor

The pinned four-second corpus from [T399](2026-09-18-frame-pacing.md) contains
240 NV12 pictures at 1280×800/60 FPS for text, pen and motion. All candidates
encode without B pictures or encoder lookahead, with eight software threads and
one-second GOPs. Software settings favor low latency: x264/x265 ultrafast and
zerolatency, VP9 realtime/cpu-used 8/lag 0, and libaom realtime/cpu-used 8/lag 0.
This is a comparison of these concrete implementations/settings, not each codec's
best possible compression efficiency. Other presets and SVT-AV1 are not timed.

The initial 54-case sweep uses quantizers 18/26/34. Refinement selects the highest
tested quantizer whose all-plane, luma and text-crop PSNR each remain within
0.5 dB of H.264 VAAPI QP 18. The search assumes approximate monotonicity; every
selected sample is actually measured. This is a quality floor, not equal
perceptual quality: some alternatives remain several dB above a floor constrained
by another region. Text legibility and motion perception need separate judgment.
RGB-to-NV12 chroma loss already exists in the reference and cannot be recovered
by a different video encoder. T419 retains lossless/RGB compression research.

| Encoder | Text Q / Mb/s | Pen Q / Mb/s | Motion Q / Mb/s |
| --- | ---: | ---: | ---: |
| H.264 VAAPI | 18 / 0.655 | 18 / 0.732 | 18 / 5.603 |
| HEVC VAAPI | 20 / 0.636 | 20 / 0.682 | 21 / 4.004 |
| libx264 | 26 / 0.943 | 26 / 1.027 | 23 / 6.211 |
| libx265 | 21 / 1.480 | 21 / 1.672 | 19 / 7.995 |
| libvpx VP9 | 32 / 0.700 | 32 / 0.772 | 32 / 3.406 |
| libaom AV1 | 44 / 0.677 | 37 / 0.820 | 27 / 3.140 |

Rates include the small Matroska container overhead across four seconds. They
are encoded-size estimates, not measured USB/Wi-Fi wire rates. The corpus differs
from the deployed baseline workload that produced roughly 29 Mb/s, so these
smaller numbers do not represent an end-to-end bandwidth reduction against it.
All selected files decode to 240 pictures using stock FFmpeg; exact encoded and
stream-copy fixture bytes are archived. The complete PSNR regions, trial commands,
coarse/refined observations and output hashes remain in the raw results.

VP9 and AV1 reduce motion bytes in this selected comparison, while offering
little advantage for the mostly static scenes. The x265 ultrafast samples use
more bytes than H.264 VAAPI at the chosen quality floor; a newer codec label
alone does not guarantee smaller output under a low-latency preset.

## Paced encoder output

Each host trial sends 240 complete NV12 frames on a 60-FPS schedule to stock
FFmpeg, collecting one framecrc packet line per picture. The first sixty frames
are warmup. Timing begins immediately before the raw write and ends when the
packet line is read: it includes pipe admission, hardware upload, encoder work,
mux/checksum work and reader scheduling. It is not a GPU-only timer. Packet PTS
must remain ordered 0..239. Source/packet clocks and exact commands are retained.

The table gives medians of three per-trial order statistics at
floor(p × (N − 1)), using only the 180 post-warmup pictures.

| Motion encoder | Output p50 ms | Output p99 ms |
| --- | ---: | ---: |
| H.264 VAAPI, default depth 2 | 17.826 | 18.671 |
| H.264 VAAPI, depth 1 | 3.273 | 4.383 |
| HEVC VAAPI, default depth 2 | 17.795 | 19.355 |
| HEVC VAAPI, depth 1 | 3.188 | 6.694 |
| libx264 | 1.586 | 2.293 |
| libx265 | 6.109 | 16.032 |
| libvpx VP9 | 3.198 | 6.048 |
| libaom AV1 | 7.198 | 59.702 |

The full series has 54 default-control trials and eighteen additional VAAPI
depth-one trials. For all eighteen paired VAAPI runs, all 240 packet timestamps,
lengths and framecrc checksums match. That is per-packet checksum equivalence,
not a cryptographic proof of byte identity. No codec/rate/quality change explains
the depth comparison. One round of software throughput includes process startup
and is preserved separately; it is not used as per-frame latency.

A separate clean concurrency series uses independent H.264 VAAPI processes on
the same GPU at one/two/four streams, three rounds each. Every worker processes
240 ordered pictures. Cells are medians across the 3/6/12 worker trials per cell,
not worst-stream or pooled percentiles.

| Concurrent encoders | Depth 2 p50 / p99 ms | Depth 1 p50 / p99 ms |
| ---: | ---: | ---: |
| 1 | 18.128 / 18.961 | 3.417 / 5.228 |
| 2 | 18.033 / 18.879 | 4.147 / 6.141 |
| 4 | 18.340 / 19.758 | 5.151 / 8.871 |

An earlier concurrency attempt overlapped host compilation and was stopped;
its exclusion reason and incomplete data remain separate. The clean 42-worker
repeat ran without host compilation. This establishes improvement at 1280×800
on this GPU, not at 4K, another VAAPI driver or a different server topology.

FFmpeg 5.1 describes async depth as maximum processing parallelism, dependent on
driver `vaSyncBuffer` support. The option is absent from FFmpeg 4.4. See the stock
[5.1 VAAPI options](https://github.com/FFmpeg/FFmpeg/blob/n5.1/libavcodec/vaapi_encode.h)
and [4.4 source](https://github.com/FFmpeg/FFmpeg/blob/n4.4/libavcodec/vaapi_encode.h).
The production adapter probes `ffmpeg -hide_banner -h encoder=NAME` once per
encoder process start, using the existing asynchronous five-second command bound.
Only a successful help response with the exact `-async_depth` option enables it.
Unsupported/failed probes omit that optional flag. There is no per-frame probe,
new FFmpeg minimum version or distro-name detection. This gate does not certify
all other project options on old FFmpeg releases.

The permanent command-boundary regression first failed with the desired depth
missing. A second regression then failed when unsupported encoders still received
the new flag; it passes after capability gating. Fake stock-help fixtures cover
stdout/stderr, absent options, misleading prose, nonzero exit and a missing
program. Existing GOP/color/quality command contracts remain tested.

## Physical decoding and profile selection

Forty-five valid trials compare five working encoder/decoder combinations over
text, pen and motion, three alternating-order rounds, four seconds warmup and
twelve seconds measurement at 60 FPS. Each cell is the median of three
per-trial feed-to-output-release percentiles. This ends at the Android output
release call, not optical display presentation.

| Encoded stream / Android decoder | Text p50 / p99 ms | Pen p50 / p99 ms | Motion p50 / p99 ms |
| --- | ---: | ---: | ---: |
| H.264 VAAPI / Unisoc hardware | 28.49 / 30.20 | 28.49 / 30.05 | 27.73 / 29.56 |
| libx264 / Unisoc hardware | 11.76 / 14.01 | 11.68 / 14.12 | 11.74 / 14.04 |
| libx265 HEVC / Unisoc hardware | 8.97 / 13.19 | 8.98 / 13.40 | 9.08 / 14.78 |
| libvpx VP9 / Unisoc hardware | 10.20 / 13.74 | 10.22 / 13.64 | 10.60 / 16.00 |
| libaom AV1 / Android software | 10.65 / 48.99 | 10.77 / 50.45 | 89.53 / 110.08 |

Every trial sent 720 measured pictures, with zero invalidations or duplicate
notifications. H.264 VAAPI notified 719, consistent with its observed final
picture delay; the other combinations notified all 720. AV1's software decoder
handles the mostly static scenes much better than motion, but still has larger
tails. Its smaller motion stream does not compensate for this tablet's decoder
delay. VP9 merits future integration research on devices with hardware support;
these results do not establish a production advantage over the explicit H.264
profile below.

App-process CPU medians were about 43–45% of one core for hardware decoding.
AV1 showed 28% during motion and 36% for text/pen **in the app process**; decoding
in a separate media process is excluded, so those smaller numbers do not show
lower total CPU or device power. Battery snapshots remain in the raw artifacts,
but these short trials cannot establish sustained charge or thermal effects.
The callback's reported render timestamp uses the sequence-derived media clock,
not a comparable monotonic presentation clock; the summary retains these raw
values but does not interpret their negative differences as latency (T414).

HEVC inventory alone proved insufficient. The selected VAAPI HEVC motion sample
(Main, 8-bit, level 4, no B frames) decodes all 240 pictures in stock software
FFmpeg, but `c2.unisoc.hevc.decoder` failed with native error 14 during warmup.
The same Android replay decoded the selected libx265 HEVC sample successfully.
The failing trial is retained and excluded from latency comparisons. T422 tracks
framing/CSD versus bitstream/driver compatibility; this experiment does not yet
establish the cause or fix. No FFmpeg patch or undocumented bitstream rewrite
is warranted from that observation.

A separate H.264 experiment isolates High/CABAC, High/CAVLC and Constrained
Baseline/CAVLC under stock VAAPI at QP 18 and async depth one. The decoded
frame-by-frame MD5, size and timestamp lines match across all three variants for
all 240 pictures in each of the text/pen/motion scenes. Encoded motion size grows
from 2,801,510 to 3,467,683 bytes (+23.8%); text/pen increases are about 6%.

Eighteen physical trials compare all three profiles at 60 and 5 FPS, with three
alternating-order rounds, two seconds warmup and ten seconds measurement.
Medians of per-trial release percentiles are:

| H.264 profile / entropy | 60 FPS p50 / p99 ms | 5 FPS p50 / p99 ms |
| --- | ---: | ---: |
| High / CABAC | 27.77 / 29.72 | 211.81 / 213.42 |
| High / CAVLC | 27.81 / 29.52 | 211.88 / 213.33 |
| Constrained Baseline / CAVLC | 11.03 / 12.68 | 11.87 / 13.05 |

High profiles notified 599/600 or 49/50 measured inputs; Constrained Baseline
notified all 600/600 and 50/50, with no invalidations/duplicates. Entropy alone
does not explain the improvement. This is evidence for a profile-dependent
one-picture delay on this decoder, not proof of a particular internal driver
algorithm. It also narrows T399's sparse-delay result to its tested streams.

Select **AMD / Intel H.264 low latency (VAAPI)** in the Linux encoder menu, or
set `encoder = "h264_vaapi_baseline"` in the host configuration. It maps to stock
`h264_vaapi -profile:v constrained_baseline -coder cavlc`, retains the selected
render node, quality, GOP, resolution and FPS, and uses the same H.264 wire
protocol. Existing `h264_vaapi`, legacy aliases and saved selections retain their
profile policy. There is no automatic codec fallback or silent config migration.
The optional in-process build rejects this choice before capture just as it
rejects its other VAAPI choices. The larger stream still uses VAAPI CQP; this
experiment does not impose a bitrate ceiling. T259 subsequently made the
uncapped policy explicit in settings; it did not change these encoder options.

The latency advantage is measured on this tablet/GPU pair. Other VAAPI drivers
must support the selected profile, and other Android decoders may behave
differently. GUI persistence, profile-to-stock-encoder mapping, command flags,
old-selection preservation and optional-build rejection have permanent tests.
The new selection/command tests were observed failing before implementation.


## Wire architecture and future integration

Production keeps its existing H.264/HEVC negotiation and Annex-B framing. VP9
and AV1 are benchmark-only. Before adding either to production:

1. Advertise verified MIME/profile/level/bit-depth/dimension/rate capabilities,
   distinguish software from hardware, then choose an intersection with an
   actually available host encoder. An old client that omits the capability
   extension must retain H.264 fallback. Negotiation cannot simply trust a listed
   MIME after the observed HEVC failure.
2. Give each codec an access-unit/config/random-access adapter. H.264 carries
   SPS/PPS; HEVC carries VPS/SPS/PPS. VP9/AV1 use their own framed samples, not
   Annex-B start-code scanning. The replay strips IVF's file/frame headers and
   preserves encoded sample boundaries; that fixture format is not a proposed
   wire protocol. Handle VP9 superframes and AV1 temporal units/sequence headers
   explicitly before production admission.
3. Use only stock library/CLI codec interfaces. Keep ordered reference pictures,
   bounded sample/config sizes, immutable ownership, generation retirement and
   a verified random-access point after loss/reconnect. A codec switch needs a
   new decoder generation/config boundary rather than reinterpreting queued bytes.
4. Add permanent shared protocol vectors, malformed/oversized sample checks,
   old-client fallback and codec-switch/reconnect tests, plus physical decode
   coverage for every promoted combination. Measure USB/Wi-Fi transport,
   sustained whole-device power and thermal behavior before automatic selection.

Android documents the codec-specific initialization contracts, including optional
VP9 CodecPrivate and AV1CodecConfigurationRecord, in
[MediaCodec](https://developer.android.com/reference/android/media/MediaCodec).
The offline fixture parser accepts the old H.264 format and a bounded MIME-tagged
version used only by the replay. Its four normal-suite tests cover compatibility,
valid config-free codecs, unsupported MIME and malformed/truncated/oversized data.
Stock [bitstream filters](https://ffmpeg.org/ffmpeg-bitstream-filters.html) produce
Annex-B parameter sets and AUD boundaries without a project FFmpeg fork.

Sustained physical power and available network-transport validation remain
tracked in T388. The broader T382 campaign is closed as `wont_fix` for now;
maintainer multi-tablet testing is outside the current scope. This research
does not establish unmeasured power or physical multi-tablet gains.

No evidence here warrants an intra-only/MJPEG production mode. T419 is the
separate task for lossless/tile/intra-image alternatives and detailed RGB fidelity.
T388 retains sustained battery tests: low app-process CPU is not low device power,
especially when software decoding runs in Android's separate media process.
The gauge's coarse steps also make these short replay snapshots insufficient.
No claim is made for Wi-Fi energy, optical latency, AV1/VP9 multi-tablet scaling
or advertised maximum decoder counts.

## Evidence and reproduction

The [artifact directory](2026-09-18-codecs/) preserves inventory, all quality
results/commands, selected exact encoded samples, fixture bytes, host pacing
traces, capability/regression logs, actual APK/source provenance and checksums.
The corpus is stored once with T399. The physical codec/profile trials used the
same exact replay APK as T399's burst cohort (SHA-256
`2a460d1b3c25a971f9589f998e479ef7c61357c913fcd3891e8f2d60f2b80420`);
its [archived source](2026-09-18-frame-pacing/burst-sources.tar.gz) and
[provenance](2026-09-18-frame-pacing/burst-provenance.json) retain the benchmark's
MIME-tagged fixture support. Each new cohort also records the verified APK hash. Coarse alternatives can be regenerated;
selected samples are retained because codec/library changes can change bytes.
Absolute temporary paths in raw commands identify the original experiment;
replace those paths when repeating it.

Run `codec-host.py` for the coarse matrix, `codec-match.py` for the documented
quality-floor search, `codec-fixtures.py` for decoder samples, `codec-latency.py`
for paced host output and `codec-concurrency.py` for 1/2/4 VAAPI processes.
Use `decoder-project.py` plus `decoder-plan.py` for the separately installed
physical replay; the executed plans accompany each raw cohort. The required
host/Android tooling is the same as T399, plus the selected stock encoder libraries
and an explicitly chosen VAAPI render node. Never silently replace missing
hardware with a software decoder and label it hardware performance.
