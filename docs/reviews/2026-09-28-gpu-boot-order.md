# T700: GPU preloading before EVDI

Blent's Linux setup now requests the currently bound display drivers before
EVDI through a separate modprobe soft dependency. This mitigates the reproduced
startup ordering failure; it does not repair Xorg's general late-glamor handling.
The affected AMD machine has not been reconfigured or rebooted. T700 remains
blocked on that native acceptance and the other maintained driver arrangements.
T222's original gamma fault remains separate.

## Behavior

`scripts/gpu-boot-order.sh` discovers DRM cards through sysfs, resolves their
provider's driver module, validates module names, deduplicates them and publishes
`blent-gpu-order.conf` atomically without replacing an existing administrator
file or symlink. It excludes EVDI/simpledrm and maps NVIDIA and virtio transport
names to their DRM modules. Missing or built-in module metadata contributes no
loadable dependency; no candidates produces an explicit warning.

The source/tarball installer, Make setup and RPM/Arch hooks invoke it before
EVDI provisioning. AppImage includes it for explicit administrator setup, without
adding privilege escalation to its user installer. The helper itself never
loads/unloads a module or restarts a desktop. See [installation](../installation.md#gpu-ordering-before-evdi-t700)
for existing configurations, driver changes and initramfs requirements.

This implements the ordering recommended by [EVDI's module guidance](https://github.com/DisplayLink/evdi/blob/33b7b3c9f7c77157c2b1b0c5a40cebe19b8ba110/module/README.md).
A [modprobe soft dependency](https://man7.org/linux/man-pages/man5/modprobe.d.5.html)
requests preloading; it is not a display-server readiness barrier or a guarantee
that a failed GPU initialization will prevent Xorg startup.

## Isolated native Linux boot evidence

A disposable QEMU/KVM q35 guest used OVMF, a private initramfs, the Ubuntu
`7.0.0-34-generic` kernel and its installed EVDI module, systemd-udevd, and
virtio-vga-gl. Mesa rendered through the host RX 6600 XT render node; the guest
had no host disk, network, input-device or physical-GPU passthrough. Guest Xorg
ran on its own `:0`. The live display server and host module/configuration state
were unchanged. The separate EVDI working repository was not used or modified.

The guest deliberately loaded `virtio_gpu` after an initial software Xorg screen
had answered `xdpyinfo`. Green boots included `softdep evdi pre: virtio_gpu`,
generated by the helper, so the same `modprobe evdi` preloaded the accelerated
GPU before server startup. Both packages print X server version `1.21.1.11`;
the package revisions below identify the actual archived/current binaries.

| Xorg Ubuntu package revision | EVDI | GPU order | Result / serial evidence |
| --- | --- | --- | --- |
| `2:21.1.12-1ubuntu1.6` | Present | Late | [Same `dix/privates.c:382` assertion; Xorg exits](artifacts/2026-09-28-gpu-boot-order/guest-red3.log) |
| `2:21.1.12-1ubuntu1.6` | Absent | Late | [Same assertion; Xorg exits](artifacts/2026-09-28-gpu-boot-order/guest-no-evdi.log) |
| `2:21.1.12-1ubuntu1.6` | Present | Preloaded | [glamor enabled at startup; Xorg survives](artifacts/2026-09-28-gpu-boot-order/guest-green.log) |
| `2:21.1.12-1ubuntu1.8` | Present | Late | [Same assertion; Xorg exits](artifacts/2026-09-28-gpu-boot-order/guest-current-red.log) |
| `2:21.1.12-1ubuntu1.8` | Present | Preloaded | [Xorg survives, post-hotplug query succeeds, real guest sysfs produces `virtio_gpu`](artifacts/2026-09-28-gpu-boot-order/guest-current-green-complete.log) |

EVDI is therefore not necessary for this isolated failure. This establishes a
startup-order mitigation for the tested modprobe path, not universal correctness
of mixed-driver startup, physical AMD hotplug or NVIDIA initialization.
[Assembly instructions and guest init](artifacts/2026-09-28-gpu-boot-order/README.md)
retain the reproduction conditions; binary images and process cores are excluded.

## Permanent regressions and measurements

The normal script suite retains 15 T700 tests in
`scripts/tests/test_installer_gpu_order.py`: driver mappings/topologies,
multiple GPUs, missing devices, configuration preservation, concurrent creation,
atomic write failures, package-hook ordering and seeded invalid-input/boundary
cases. Tests were added and observed failing before their corresponding fixes.
The artifact directory retains the [initial red run](artifacts/2026-09-28-gpu-boot-order/regression-red.txt)
and individual write, metadata, topology and publication failure runs.

- Normal script discovery: 348 tests, success, one existing Windows-only skip.
- Tooling integration: 35 of 36 initially passed; packaging copied the helper
  while its virtio mapping was being edited, causing a content mismatch. The
  same failed test passed after edits stopped. Both logs are retained.
- Final scoped instrumented runs: 42 installer tests, four EVDI setup tests,
  28 AppImage tests and one distribution test passed, including the 15 final
  T700 tests. [All nine changed production functions](artifacts/2026-09-28-gpu-boot-order/coverage-affected-functions.json)
  reached 100% executable-line coverage individually. The manifest and complete
  scoped report are retained; uncovered functions outside this selection are
  not a whole-project coverage pass.
- Final distribution/notices check and Rust formatting passed. The complexity
  gate reported 6,511 functions with none exceeding nine; six coverage-inventory
  tests passed, and the ledger has 54 unique rows in its two lifecycle tables.
- Native host discovery generated `softdep evdi pre: amdgpu` in an external
  staging directory. [Read-only `modprobe --show-depends`](artifacts/2026-09-28-gpu-boot-order/native-modprobe-plan.txt)
  placed amdgpu before EVDI. No host configuration was installed.

The unrelated Make target's unconditional EVDI-capacity overwrite was recorded
as T711 for its own regression and fix commit. It is not resolved here.
