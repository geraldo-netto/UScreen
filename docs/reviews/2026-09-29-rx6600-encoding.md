# RX 6600 XT encoding configuration

On 2026-09-29, the maintainer requested that the RX 6600 handle Blent video encoding, with a GPU selector tracked for later implementation as T727. Desktop composition was explicitly outside this change.

## Configuration and validation

The live user configuration was backed up to `/home/netto/.config/blent/config.toml.before-rx6600-20260929-172631` with mode 0600. Only these two settings were edited under the existing configuration file lock:

```toml
encoder = "h264_vaapi_baseline"
vaapi_device = "/dev/dri/by-path/pci-0000:03:00.0-render"
```

Previously they were `auto` and `/dev/dri/renderD128`. The PCI path resolves to the RX 6600 XT render node and avoids relying on its current numeric node assignment. Resolution 1280×800, 60 FPS, quality 18 and other settings were preserved. Blent's user service was restarted at approximately 17:26:42 CEST; the tablet reconnected and resumed video. The display layout remained a 3840×2160 primary display with the tablet at 1280×800 to its right.

Validation performed:

- `vainfo --display drm --device /dev/dri/by-path/pci-0000:03:00.0-render` identified RX 6600 XT and advertised H.264 Constrained Baseline encoding.
- A separate bounded 120-frame synthetic encode at 1280×800 with bundled FFmpeg and its existing private-library environment succeeded. It used the PCI device path, VAAPI, Constrained Baseline/CAVLC, no B frames, and QP18. This was a capability check, not a desktop latency benchmark.
- The live FFmpeg process used `-vaapi_device /dev/dri/by-path/pci-0000:03:00.0-render`, `-c:v h264_vaapi`, `-profile:v constrained_baseline`, `-coder cavlc` and `-async_depth 1`.
- `/proc/207585/fdinfo` identified DRM PCI device `0000:03:00.0`. Its encode-engine counter advanced; one eight-second sample measured 9.27% encode-engine busy time and FFmpeg CPU usage equivalent to 3.25% of one core.
- Service state was active with zero automatic restarts. Render ACKs continued: the initial three hardware-stream intervals reported packet-ready-to-render-ACK p50 16.9–17.1 ms and p95 19.7–20.2 ms, with 195–221 ACK samples per interval.
- Final configuration readback retained the explicit encoder and stable device path after daemon settings saves.

Before the change, three recent software-stream intervals reported p50 16.3–16.5 ms and p95 18.3–19.0 ms. Content and timing were not controlled, so these samples do not establish a latency improvement or regression. Packet-ready-to-render-ACK excludes capture and encoding. This change fulfills the requested GPU assignment; it is not evidence that whole-desktop responsiveness improved.

Cinnamon/Xorg still renders on Radeon 610M. EVDI capture and CPU-side conversion remain active. The experimental GPU capture helper was not enabled; its same-device guard and T578 cross-device restriction remain intact. VAAPI CQP does not enforce the stored bitrate ceiling.

Startup logged unavailable KWin and an X11 input-mapping readiness warning. This check validated encoding and video ACKs, not touch/pen mapping or optical presentation. No input settings were changed or native input acceptance claimed.

## GPU selector follow-up

`common/src/model.rs` stores a raw `vaapi_device` path; the current `gui/src/main.rs::setting_encoder` exposes codec selection without adapter selection. T727 requests a named, capability-aware encoding GPU selector using platform adapters and a portable user-facing contract. This follow-up does not request moving desktop composition, bypassing T578, or enabling unsupported platforms.

To return to automatic encoder selection, change only `encoder` back to `auto` and restart the user service; the stable RX render path can remain. To restore the exact prior two settings, also restore `vaapi_device` to `/dev/dri/renderD128`, verifying its device identity first. Preserve settings changed subsequently rather than blindly copying the whole backup.

This was an existing configuration feature, not a behavioral code fix. No production code or permanent test was altered. T728 separately corrected a stale encoder-default statement in `docs/llms.txt` after checking `FileConfig::default` and the existing automatic-selection documentation.
